Management Protocols

Each device can be managed via one of four protocols. Set the Management Type when adding or editing a device.

eAPI (HTTPS) — Recommended

Arista's REST/JSON API over HTTPS (port 443). Provides the richest telemetry: interfaces, CPU, memory, temperature, and version information.

EOS config required:

management api http-commands
  no shutdown
SSH

Connects over SSH (port 22) and parses CLI output. Works on any device with SSH enabled. Telemetry is parsed from show command text.

EOS config required:

username admin privilege 15 secret <pass>
gNMI / TerminAttr

gRPC Network Management Interface via Arista's TerminAttr daemon (default port 6030). Used in production environments where eAPI is unavailable or telemetry streaming is preferred.

What is collected:

  • Interface up / down counts
  • Device reachability status

EOS configuration:

daemon TerminAttr
  exec /usr/bin/TerminAttr \
    -grpcaddr=mgmt/0.0.0.0:6030 \
    -allowed_ips=0.0.0.0/0
  no shutdown

Replace mgmt with your management VRF, or use 0.0.0.0:6030 if the management interface is in the default VRF.

CVP

Delegates management to CloudVision Portal. Kármán tracks these devices in inventory but does not push configuration directly — changes go through CVP.

gNMI / TerminAttr — Detail

How the connection works
  1. Kármán performs an SSL probe to the gNMI port to detect whether the server uses TLS.
  2. If TLS is confirmed, the device certificate is fetched and used as the trusted root (TOFU — Trust On First Use). No pre-installed CA certificate is required.
  3. If no TLS is detected (common on vEOS-lab), the connection falls back to plaintext gRPC automatically.
  4. The gNMI Capabilities RPC is optional and may return UNIMPLEMENTED on some TerminAttr versions — this is handled gracefully and does not prevent collection.
Data paths used

Kármán uses Arista's eos_native origin rather than OpenConfig. OpenConfig paths require a full CloudVision subscription to be populated; eos_native Sysdb paths are always available.

DatagNMI path
Interface up / down status eos_native:/Sysdb/interface/status/eth/phy/slice/1/intfStatus

On production deployments with a CVP licence, OpenConfig paths (/interfaces, /system, /components) will also return EOS version, model, serial number, and temperature sensors.

Configurable port

The default gNMI port is 6030. If your TerminAttr is bound to a different port, set the gNMI Port field when adding or editing the device. The field is only shown when the management type is gNMI / TerminAttr.

Port conflict: TerminAttr vs management api gnmi

EOS has two gNMI options that cannot share port 6030:

  • management api gnmi — EOS native gNMI (no TerminAttr daemon needed)
  • daemon TerminAttr — Arista's streaming telemetry agent

Use one or the other. If both are configured, TerminAttr will fail to bind and restart repeatedly (PROCESS_DELAYRESTART). To use TerminAttr, remove management api gnmi from the config.

Required Python package
pip install pygnmi>=0.8.0

Already included in requirements.txt. The gNMI connector disables itself gracefully if pygnmi is not installed.

Network Topology

The Topology page discovers and visualises physical connectivity between devices using LLDP. Click Discover Topology to query all managed devices and build the graph in real time.

Graph Controls
  • Click a node — opens the side panel showing role, IP, model, management type, and directly connected neighbours.
  • Double-click a node — navigates to the device detail page.
  • Click a link table row — highlights the corresponding edge in the graph.
  • Fit — re-centres and zooms the graph to fit all nodes.
  • Export — saves the current graph as a PNG image.
LLDP Discovery & Fallback

Kármán queries each device for LLDP neighbours using the best available protocol:

  1. gNMI (OpenConfig) — tried first for gNMI/TerminAttr devices. Requires a CVP licence to populate; empty on bare vEOS-lab.
  2. SSH fallback — if gNMI returns no LLDP data, Kármán falls back to show lldp neighbors detail over SSH.
  3. eAPI — used directly for eAPI-managed devices.

The LLDP Discovery Status table (below the link table) shows which source was used per device and how many neighbours were found.

Notes
  • Management interfaces (e.g. Management0, Management1) are automatically excluded — only data-plane links are shown.
  • Each physical link is de-duplicated regardless of which device reported it first, so the same cable never appears twice.
  • Nodes that appear as LLDP neighbours but are not in the Kármán inventory are added to the graph automatically as unknown nodes.
  • LLDP must be enabled on the devices: lldp run (enabled by default on EOS).

API Endpoints

GET /api/stats

Returns platform statistics including device counts, configlet counts, and task status.

curl http://localhost:5000/api/stats

Response:

{
  "devices": {
    "total": 25,
    "cvp_managed": 5,
    "custom_managed": 20
  },
  "configlets": {"total": 32},
  "tasks": {
    "total": 15,
    "pending": 3,
    "completed": 12
  }
}
GET /api/topology

Returns static node list from the device inventory (no live LLDP query).

curl http://localhost:5000/api/topology
GET /api/topology/discover

Actively queries all managed devices via LLDP to build the live topology. Returns nodes, links, per-device discovery status, and summary stats. This is what the Topology page calls when you click Discover Topology.

curl http://localhost:5000/api/topology/discover

Response:

{
  "success": true,
  "topology": {
    "nodes": [{"id": "switch3", "role": "unknown", "ip": "192.168.2.13", ...}],
    "links": [{"from": "switch5", "from_interface": "Ethernet1", "to": "switch3", "to_interface": "Ethernet2", ...}]
  },
  "stats": {"total_nodes": 5, "total_links": 3},
  "device_status": [{"hostname": "switch5", "lldp_source": "ssh_fallback", "neighbor_count": 2, "error": null}]
}

Getting Help

Troubleshooting
  • Check the logs/ directory for application logs
  • Review WEB_INTERFACE.md for web-specific issues
  • Verify all dependencies: pip install -r requirements.txt
  • Ensure database permissions: chmod 644 custom-cvp.db
Common Issues
  • Port in use: Change port in .env or kill existing process
  • Database locked: Close other instances of the application
  • Templates not found: Run from project root directory
  • Connection failed: Verify device credentials and network connectivity
gNMI / TerminAttr Issues
  • Device shows DOWN despite TerminAttr running: Check that -grpcaddr includes the correct VRF. If Management1 is in VRF mgmt, use -grpcaddr=mgmt/0.0.0.0:6030. Without the VRF prefix, TerminAttr binds in the default VRF and is unreachable.
  • TerminAttr flapping / PROCESS_DELAYRESTART: Port 6030 is already in use by management api gnmi. Remove one — they cannot coexist. Check with: show daemon TerminAttr
  • GRPC ERROR: Not implemented yet: This TerminAttr version does not implement gNMI Capabilities. Kármán handles this automatically — it is a warning, not a fatal error. If all RPCs fail, verify the VRF setting.
  • Interface counts show 0: Run gnmic -a <ip>:6030 --insecure -u admin -p <pass> get --path "eos_native:/Sysdb/interface/status/eth/phy/slice/1/intfStatus" --encoding json from the Kármán host to confirm the path returns data.
  • pygnmi not installed: Rebuild the Docker image: docker compose down && docker compose build && docker compose up -d
