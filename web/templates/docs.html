The dashboard polls all devices concurrently every ~30 seconds using a background daemon thread. Results are cached in SQLite and served instantly to the browser.

Interface Telemetry tab (device detail)

Only shown for devices with management type gNMI. Displays a stepped line chart of interface active status over time (1h/6h/24h) and a link flap count table, backed by Prometheus/gnmic data.

Per-device sync

The Sync button on the device detail page triggers an immediate running-config backup. The config is stored as a configlet named <hostname>-running-config and the compliance status is updated.

Configlets

Configlets are named EOS configuration snippets stored in Kármán with full versioning. Every save generates a new version entry with SHA256 hash, timestamp, and optional change reason.

  • Files are stored on disk at ./configlets/<name>.cfg
  • Running-config backups are automatically stored as <hostname>-running-config.cfg
  • Configlets can be assigned to devices and deployed via Tasks
  • History tab shows every version — click any version to diff against the current
Tasks / Change Control
Lifecycle
PENDING IN PROGRESS COMPLETED or FAILED or ROLLED BACK
  • Tasks target one or more devices and carry a set of config changes to apply
  • Execution is logged per-device — partial failures are captured without blocking other devices
  • Rollback information is stored at task creation time so changes can be reversed
  • Only admins can execute or cancel tasks

Scheduled backups

Configure at Admin → Settings → Config Backup. Choose daily or weekly, set the UTC hour, and Kármán's backup background thread will capture running configs automatically. Each backup stores the full config as a configlet and updates the Last Backup timestamp on the Devices page.

Diff view

Click View Diff on any DRIFT device to see a unified diff between the previous and current config snapshots — added lines are highlighted green, removed lines red.

BGP Dashboard

The BGP page shows peer state for every BGP neighbor across all devices and VRFs. Data is collected during the background telemetry cycle and cached. The page falls back to a live concurrent query if the cache has not yet been warmed.

Peer state badges
Established Active Connect OpenSent OpenConfirm Idle Unknown
  • Filter by device, VRF, or state using the filter bar — filtering is client-side (instant, no reload)
  • BGP state changes from Established → any other state trigger an in-app notification to all admins
  • BGP is collected via eAPI for eAPI and SSH-managed devices; gNMI devices fall back to eAPI for BGP
Threshold Alerting

Alert rules are evaluated every ~30 seconds by the alert background thread against the live telemetry cache. Navigate to Admin → Alert Rules to manage rules and view recent events.

Alert types
TypeThresholdSource metric
cpu% (e.g. 80)System CPU usage percent
memory% (e.g. 90)System memory usage percent
interface_down_countcount (e.g. 2)Number of interfaces in down state
device_down—Device unreachable (boolean)
temperature_critical—Any sensor in critical state (boolean)
Rule options
  • Scope — all applies to every polled device; a hostname targets one device
  • Cooldown — minimum minutes before a re-notification for an already-firing event
  • Email — send email to all admins in addition to in-app notification
  • Enable/disable — pause a rule without deleting it
  • Events have firing and resolved states — resolution is automatic when the condition clears
Zero Touch Provisioning (ZTP)
How it works
  1. New Arista switch boots with no startup config and enters ZTP mode
  2. Switch sends a DHCP request; server returns Option 67 pointing to /ztp/script
  3. EOS downloads and executes the Python script
  4. Script writes the base config to /mnt/flash/startup-config
  5. Script calls back to POST /api/devices/register
  6. Kármán adds the device to inventory, notifies all admins, and the device appears on the dashboard within one telemetry cycle
DHCP options
Existing DHCP server

Add Option 67 to your DHCP server config:

option bootfile-name "http://<karman-ip>:5000/ztp/script";
Built-in DHCP server

Enable the dnsmasq-backed server in Admin → ZTP. Requires dnsmasq installed and network_mode: host in docker-compose.yml.

Device-resident Agent (.swix)

The Kármán agent is a lightweight Python daemon that runs directly on your EOS switches. It sends periodic heartbeats and immediately notifies Kármán when it detects a configuration wipe — letting you know a device may need re-provisioning before it causes an outage.

How it works
  1. Agent checks in via POST /api/devices/checkin every 5 minutes
  2. On each check-in, Kármán updates the Active badge on the Devices page
  3. If the running config falls below 20 meaningful lines (factory reset / write erase), the agent sends a config_lost event
  4. Kármán triggers a backup run and sends an in-app notification to all admins
Installation options
Automatic (via ZTP)

When a device is provisioned via ZTP the script automatically downloads karman_agent.py to /mnt/flash/ and adds a daemon karman-agent stanza to the startup-config. No manual steps needed.

Manual (.swix)

Run on the switch:

copy http://<karman-ip>:5000/karman-agent.swix flash:
extension karman-agent.swix
copy installed-extensions boot-extensions

The .swix persists across write erase and software upgrades.

Topology

The topology page runs show lldp neighbors detail across all reachable devices and builds an interactive graph. Nodes are colour-coded by role (spine/leaf/border/core/access). Drag nodes to rearrange; zoom with scroll wheel. Only devices with eAPI or SSH management types contribute LLDP data — gNMI-only devices appear as isolated nodes if LLDP is not polled separately.
